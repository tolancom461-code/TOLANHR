# Worker Photo Audit V2 Update — 2026-09-05

Incremental update for the already-installed worker photo feature in the main application.

## Scope

Main application only. No biometric-service files are included.

## What changed

- Successful first worker-photo upload is recorded as `ADD_WORKER_PHOTO`.
- Successful replacement is recorded as `REPLACE_WORKER_PHOTO`.
- Dual-write remains active:
  - legacy `audit_log` for compatibility with existing screens;
  - `audit_log_v2` for the durable actor snapshot and richer audit metadata.
- `audit_log_v2.actor_snapshot` captures the acting user's identity at the time of the action through the existing `actorFromUser()` flow (including name/username/role fields available on the authenticated user).
- `audit_log_v2.logged_at` continues to be generated by TiDB using the existing table default.
- Request ID, IP address, User-Agent, worker code, worker ID, operation type, and a safe storage key are recorded through the existing V2 audit service.
- No image bytes, Base64 payload, or public/signed photo URL is stored in either audit record.
- The worker `photo_url` update and both audit writes now run inside one database transaction after Object Storage upload succeeds.
  - If Audit V2 fails, the database photo reference is rolled back and the worker keeps the previous photo.
  - The already-uploaded Object Storage object may remain orphaned if the DB transaction fails; it is not linked to the worker and does not replace the current photo.
- Accountant (`accountant`) remains included in the approved worker-photo management roles.

## Database

No SQL, migration, schema change, or Drizzle push is included or required.

## Files

- `server/routers/workers.ts`

## Audit semantics

Only committed data changes are audited. Selecting a local file, opening the preview, cancelling the picker, or viewing a photo does not create an audit entry because those actions do not change worker data.
