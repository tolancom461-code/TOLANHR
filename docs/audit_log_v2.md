## 1. لماذا سجل جديد؟

`audit_log` القديم (لا يزال يعمل ولن يُحذف) كان يسجّل فقط: من نفّذ، ما نوع العملية، القيم قبل/بعد كنص JSON حر. كان يعاني من ثلاث ثغرات جوهرية مؤكَّدة بفحص الكود الفعلي:

1. **هوية المنفذ غير مجمَّدة** — يعتمد على `JOIN` حي مع جدول `users`، فلو تغيّر دور المستخدم لاحقاً تتغيّر كل سجلاته التاريخية معه.
2. **لا ذرية** — 76 نقطة `logAudit()` بالكود القديم كانت جميعها استدعاءً منفصلاً بعد العملية الأصلية، بدون أي `transaction`. فشل كتابة التدقيق لا يوقف نجاح العملية.
3. **لا أسماء تاريخية** — حذف عامل أو مجموعة يفقد اسمها من السجلات القديمة لاحقاً.

`audit_log_v2` جدول مستقل بالكامل يعالج هذه الثغرات الثلاث تحديداً، بالإضافة لبقية متطلبات الوثيقة.

---

## 2. مبدأ التشغيل المزدوج (Dual-Write)

خلال فترة الانتقال، **الجدولان يعملان معاً بالتوازي**:

```
database.transaction(async (tx) => {
  1) تنفيذ العملية الفعلية (INSERT/UPDATE/DELETE على الجدول الحقيقي)
  2) db.logAudit({ ...، tx })     ← الجدول القديم audit_log
  3) db.logAuditV2({ ...، tx })   ← الجدول الجديد audit_log_v2
});
```

كلاهما داخل نفس المعاملة: إما ينجح كل شيء معاً، أو يتراجع كل شيء معاً. **لا يُعدَّل ولا يُحذف أي شيء من `audit_log` القديم** — يبقى للقراءة والمقارنة كما هو مقرر بقسم 12 من الوثيقة.

## 3. بنية الجدول (34 عمود)

منشأ فعلياً في TiDB ومطابق لـ `drizzle/schema.ts` (`auditLogV2`). الأقسام الأربعة:

### أ. هوية الحدث والكيان
| العمود | الوصف |
|---|---|
| `event_uuid` | معرّف عالمي فريد للحدث (UUID) |
| `logged_at` | وقت الكتابة بدقة أجزاء الثانية `DATETIME(6)` |
| `business_event_at` | وقت الحدث التجاري الفعلي (مثال: وقت البصمة، وليس وقت حذفها) |
| `action_category` | تصنيف عام: `CREATE`, `UPDATE`, `DELETE`, `RESTORE`, `APPROVE`, `REJECT`, `ACTIVATE`, `DEACTIVATE`, `ARCHIVE`, `ASSIGN`, `TRANSFER`, `IMPORT`, `EXPORT`, `RECALCULATE`, `GRANT_PERMISSION`, `REVOKE_PERMISSION`, `CHANGE_ROLE` |
| `action_name` | اسم تفصيلي، مثال: `DELETE_ATTENDANCE` |
| `description` | وصف عربي جاهز للعرض المباشر |
| `table_name` / `entity_type` / `record_id` / `record_key` | الجدول والكيان والمعرّف + كودات تعريفية ثابتة (`{ workerCode: 'W109' }`) |

### ب. المنفذ ومصدر العملية
| العمود | الوصف |
|---|---|
| `actor_user_id` | فارغ لعمليات `SYSTEM` |
| `actor_snapshot` | لقطة JSON مجمَّدة (id, fullName, username, email, role, loginMethod) — **لا تتأثر بتعديل الحساب لاحقاً** |
| `source` | `WEB`, `MOBILE`, `API`, `SYSTEM`, `IMPORT` |
| `ip_address` / `user_agent` | تُستخرج تلقائياً من `ctx.req` داخل `AuditService` — لا حاجة لتمريرها يدوياً من كل راوتر |
| `request_id` | موحّد لكل طلب HTTP، يُولَّد مرة واحدة في `server/_core/context.ts` |
| `parent_event_uuid` / `batch_id` | لربط العمليات الجماعية بسجل رئيسي |

### ج. القيم والتغييرات والحماية
| العمود | الوصف |
|---|---|
| `before_values` / `after_values` | لقطات JSON كاملة (بعد إخفاء الحقول السرية تلقائياً) |
| `changed_fields` | يُحسب تلقائياً — فقط الحقول التي تغيّرت فعلاً، بصيغة `{ field: { old, new } }` |
| `reason_code` / `reason_text` | **إلزامي** لعمليات: `DELETE`, `RESTORE`, `REJECT`, `DEACTIVATE`, `ARCHIVE`, `GRANT_PERMISSION`, `REVOKE_PERMISSION`, `CHANGE_ROLE`, `TRANSFER` — تُرفض العملية برمجياً بدونه |
| `row_hash` | بصمة SHA-256 مستقلة لكل سجل (راجع القرار أدناه بخصوص `previous_hash`) |

## 4. قرار تصميمي مهم: لا سلسلة بصمات صارمة

الوثيقة الأصلية اقترحت `previous_hash` يربط كل سجل بالسجل الذي قبله مباشرة (سلسلة على طراز دفتر الأستاذ/blockchain). **تم استبدال هذا عمداً** بسبب:

- TiDB قاعدة موزّعة؛ كتابتان متزامنتان من مستخدمين مختلفين لا يوجد بينهما ترتيب "سابق/تالٍ" واضح بدون قفل صريح.
- فرض القفل يعني أن أي عمليتين بالنظام (حتى لمستخدمين مختلفين تماماً) يجب أن تنتظرا دورهما بالتسلسل — اختناق أداء حقيقي.
- الحماية الأساسية من العبث أصلاً تأتي من `SEC-001` (صلاحية `INSERT`/`SELECT` فقط للتطبيق على الجدول — بند مؤجَّل، راجع القائمة).

**البديل الحالي:** `row_hash` مستقل لكل سجل (من محتواه فقط). عمود `previous_hash` **موجود بالجدول لكن غير مُستخدَم حالياً** — محجوز لمرحلة لاحقة (نقاط تفتيش دورية بدل تسلسل لكل سجل).

## 5. `AuditService` — الخدمة المركزية

الملف: `server/db/audit-v2.ts`. **قاعدة صارمة: لا يُكتب INSERT إلى `audit_log_v2` من أي مكان آخر غير هذه الخدمة.**

### الدالة الرئيسية: `logAuditV2(params)`
تتولى تلقائياً:
- توليد `event_uuid` و`row_hash`
- إخفاء الحقول السرية (`password`, `qrToken`, `apiKey`...) من أي لقطة قبل الحفظ
- بناء `actor_snapshot` من `ActorInfo`
- حساب `changed_fields` من `before/after` (إلا لو مُرِّرت جاهزة)
- استخراج `ip_address` و`user_agent` من `ctx.req`
- **فرض `reason_text`** لو كانت `actionCategory` ضمن القائمة الإلزامية (يرمي خطأ فوراً، قبل أي محاولة كتابة)
- دعم `tx` اختيارية: لو مُرِّرت، فشل الكتابة يوقف كل شيء (rollback)؛ لو لم تُمرَّر، الكتابة best-effort (توافقية مؤقتة مع الراوترات غير المحوَّلة بعد)

### دالة مساعدة: `actorFromUser(ctx.user)`
تحوّل مستخدم tRPC إلى `ActorInfo` جاهز لـ `logAuditV2`.

### دالة مساعدة: `diffChangedFields(before, after, allowedFields?)`
تُستخدم مباشرة عند الحاجة لحساب الفروق يدوياً قبل الاستدعاء (مثال: `UPDATE_USER`).

## 7. بنود مؤجَّلة عمداً (بقرار موثَّق، وليست منسية)

| البند | السبب |
|---|---|
| صلاحية DB مقيّدة (INSERT/SELECT فقط) لـ `audit_log_v2` | يحتاج اتصال DB ثانٍ بصلاحيات منفصلة — بنية تحتية غير موجودة حالياً (المشروع يستخدم مستخدم DB واحد شبه-root لكل شيء) |
| جدول `security_event_log` منفصل (محاولات فاشلة/مرفوضة أمنياً) | مضاعفة كاملة للنطاق — نظام ثانٍ مستقل بجدول وراوتر وصلاحيات |
| نقاط تفتيش دورية للبصمة (`previous_hash`) | يحتاج `cron`/scheduler غير موجود بالمشروع حالياً |
| آلية `AUDIT_CORRECTION` (تصحيح سجل قديم دون تعديله) | تُضاف عند ظهور أول حاجة فعلية لها |

## 8. مرجع سريع للحقول الممنوع تسجيلها (SEC-004)

`password`, `passwordHash`, `accessToken`, `refreshToken`, `sessionToken`, `qrToken`, `apiKey`, `secret`, `secretKey`, `token`, `otp`, `otpCode` — محذوفة بالكامل (وليس مُخفاة فقط) من أي لقطة قبل الحفظ، عبر `redactSecrets()` داخل `AuditService`.
