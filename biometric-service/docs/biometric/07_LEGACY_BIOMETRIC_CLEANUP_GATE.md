# بوابة تنظيف وإزالة نظام البصمة القديم قبل الدمج

**تحديث 2026-08-29:** البوابة لم تبدأ بعد. اكتشاف جداول DB فارغة لا يغيّر شرط فحص مراجع الكود قبل أي حذف/تعديل. لا يوجد إذن تنظيف حاليًا.

**الحالة:** قاعدة إلزامية معتمدة  
**تاريخ الاعتماد:** 2026-08-23  
**المرجع الأعلى:** `00_BIOMETRIC_MASTER_PLAN.md`

> هذه الوثيقة يجب قراءتها وتنفيذها بعد اكتمال واختبار `biometric-service` المستقل، وقبل بدء أي ربط بين نظام البصمة الجديد وبقية البرنامج.

## 1. القرار الملزم

يوجد في المشروع Prototype قديم للبصمة متداخل مع أجزاء من البرنامج الحالي. أثناء بناء واختبار النظام الجديد المستقل **لا نحذف ولا نعدل هذا الـPrototype** حتى لا نعرض البرنامج القائم لأي تأثير غير مقصود.

بعد اكتمال النظام الجديد واختباره واعتماده، وقبل بدء الدمج، توجد مرحلة مستقلة إلزامية اسمها:

```text
LEGACY BIOMETRIC CLEANUP GATE
```

ولا يسمح بالانتقال إلى مرحلة الدمج قبل اجتيازها.

التسلسل الإلزامي:

```text
بناء biometric-service المستقل
        ↓
اختبار الجهاز الحقيقي
        ↓
اختبار النظام المستقل بالكامل
        ↓
اعتماد النظام المستقل
        ↓
STOP
        ↓
فحص واعتماديات ملفات البصمة القديمة
        ↓
عرض خطة الحذف/التنظيف على صاحب المشروع
        ↓
موافقة صريحة
        ↓
إزالة Prototype القديم بأمان
        ↓
اختبار البرنامج الحالي كاملًا بعد الإزالة
        ↓
التأكد أن QR والحضور والرواتب وبقية النظام تعمل دون تغيير
        ↓
STOP + موافقة صريحة جديدة
        ↓
بدء الدمج مع biometric-service الجديد
```

## 2. قاعدة حماية البرنامج الحالي

**يمنع لمس أي كود في البرنامج الحالي إذا كان هناك احتمال ولو ضئيل أن يؤثر على تشغيله، إلا ضمن مرحلة تنظيف مستقلة وبعد فحص وموافقة صريحة.**

لذلك أثناء بناء `biometric-service`:

- لا نعدل ملفات الـPrototype القديمة.
- لا نحذفها.
- لا نفصل Imports منها داخل ملفات التشغيل الحالية.
- لا نغير Routes الحالية بسبب النظام الجديد.
- لا نغير `package.json` الخاص بالتطبيق القائم بسبب تشغيل النظام الجديد إذا كان التغيير قد يؤثر على التطبيق.
- لا ننفذ Migration قديم أو جديد بدون موافقة.

النظام الجديد يبنى داخل مجلد مستقل في جذر المشروع:

```text
/biometric-service
```

ويعامل كتطبيق مستقل له تشغيله واختباراته وإعداداته الخاصة.

## 3. ملفات Prototype القديمة المرشحة للإزالة لاحقًا

هذه الملفات تم التعرف عليها كملفات خاصة بالـPrototype القديم. **وجودها في هذه القائمة لا يعطي إذنًا بحذفها الآن.**

### اختبارات ومحاكي Prototype القديم


الوثائق التاريخية لا يلزم حذفها تلقائيًا؛ يمكن نقلها إلى Archive بدل حذفها إذا كانت مفيدة كسجل تاريخي. القرار النهائي يعرض قبل التنفيذ.

## 4. ملفات أساسية تحتوي نقاط ربط قديمة — لا تُحذف

الملفات التالية هي أجزاء أساسية من البرنامج الحالي. **ممنوع حذفها.** عند مرحلة التنظيف، وبعد الموافقة فقط، يتم فحص وإزالة الأسطر الخاصة بالـPrototype القديم منها بدقة:

```text
server/_core/index.ts
server/routers/index.ts
server/db.ts
client/src/App.tsx
package.json
```

نقاط الربط المعروفة وقت التوثيق تشمل:

- `registerZktecoAdmsRoutes` داخل `server/_core/index.ts`.
- استدعاء `runBiometricMigration()` عند Startup داخل `server/_core/index.ts`.
- تسجيل `biometricRouter` داخل `server/routers/index.ts`.
- تصدير `server/db/biometric` من `server/db.ts`.
- Import/Route لصفحة `BiometricDevices` داخل `client/src/App.tsx`.
- Script باسم `biometric:simulate` داخل `package.json`.

هذه القائمة **Baseline** وليست بديلًا عن إعادة الفحص؛ قبل الحذف الفعلي يجب تشغيل بحث اعتماديات جديد لأن المشروع قد يتغير أثناء بناء النظام الجديد.

## 5. شروط بدء مرحلة التنظيف

لا تبدأ إزالة الـPrototype القديم إلا إذا تحققت جميع الشروط التالية:

- [ ] `biometric-service` الجديد مكتمل كنظام مستقل.
- [ ] الجهاز الحقيقي اتصل بنجاح.
- [ ] استقبال الحركات الخام تم اختباره.
- [ ] التخزين ومنع التكرار والتشخيص تم اختبارها حسب الخطة المعتمدة.
- [ ] يوجد تقرير اختبار نهائي للنظام المستقل.
- [ ] لم نعد بحاجة لأي وظيفة حصرية داخل Prototype القديم، أو تم نقل الفكرة المطلوبة إلى النظام الجديد بشكل مستقل.
- [ ] تم إنشاء قائمة اعتماديات حديثة لكل ملف قديم.
- [ ] تم تحديد أي References داخل ملفات البرنامج الحالي.
- [ ] تم إعداد خطة Rollback/نسخة مرجعية قبل التنظيف.
- [ ] تم عرض قائمة الحذف والتعديلات الدقيقة على صاحب المشروع.
- [ ] صدرت موافقة صريحة على التنفيذ.

## 6. طريقة الإزالة الآمنة

الإزالة ليست عملية `rm` جماعية. ترتيبها:

1. إعادة فحص كل Import/Route/Export/Script مرتبط بالـPrototype القديم.
2. تصنيف العناصر إلى:
   - ملف خاص بالـPrototype يمكن حذفه.
   - ملف أساسي يحتاج إزالة Reference فقط.
   - وثيقة تاريخية تحفظ/تؤرشف.
3. عرض Diff/خطة التغيير قبل التنفيذ.
4. أخذ الموافقة الصريحة.
5. إزالة نقاط الربط القديمة من الملفات الأساسية بأقل تغيير ممكن.
6. حذف الملفات التي أصبحت بلا References فقط.
7. عدم تشغيل أي Migration حذف تلقائي.
8. اختبار Build/Typecheck/Tests الخاصة بالبرنامج الحالي.
9. اختبار مسارات التشغيل الحساسة، وعلى الأقل:
   - تشغيل السيرفر.
   - تسجيل الدخول.
   - QR.
   - الحضور والانصراف الحالي.
   - العمليات اليدوية المستخدمة.
   - المالية/الرواتب بالقدر الذي تسمح به بيئة الاختبار.
10. إعادة بحث شامل للتأكد من عدم بقاء References تنفيذية للـPrototype القديم.
11. توثيق النتيجة.

## 7. قاعدة قاعدة البيانات أثناء التنظيف

إزالة كود Prototype القديم **لا تعني حذف جداول أو أعمدة قاعدة البيانات تلقائيًا**.

أي `DROP TABLE` أو `ALTER TABLE` أو حذف بيانات هو قرار منفصل تمامًا ويتطلب:

- فحص TiDB الفعلي.
- إثبات أن العنصر لم يعد مستخدمًا.
- عرض SQL قبل التنفيذ.
- موافقة صريحة مستقلة.

جدول `biometric_devices` الحالي لا يعتبر تلقائيًا جزءًا يجب حذفه، لأنه قد يكون صالحًا للنظام الجديد. القرار يؤخذ بعد اكتمال تصميم `biometric-service`.

## 8. شرط نجاح بوابة التنظيف

تعتبر البوابة ناجحة فقط إذا تحقق التالي:

```text
Prototype القديم لم يعد له مسار تنفيذي داخل البرنامج الحالي
+
البرنامج الحالي يعمل كما كان قبل التنظيف
+
لا يوجد تغيير غير مقصود على QR / Attendance / Finance
+
لا توجد Migration بصمة قديمة تعمل عند Startup
+
تم توثيق كل ما أزيل أو أبقي
```

## 9. ممنوع بدء الدمج قبل هذه البوابة

حتى لو كان `biometric-service` الجديد ناجحًا 100%، **لا يبدأ Bridge ولا ربط Workers ولا Attendance ولا QR قبل إكمال تنظيف الـPrototype القديم والتحقق من سلامة البرنامج الحالي وأخذ موافقة صريحة جديدة.**

هذه قاعدة معمارية، وليست خطوة اختيارية.
